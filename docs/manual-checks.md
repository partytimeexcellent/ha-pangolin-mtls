# Advanced connection checks

The [installation tutorial](installation.md#8-activate-and-perform-the-short-installation-checks) contains the routine minimum: reject a fresh request without a certificate, connect through Companion, and verify the external path over cellular. This page is for diagnosis, changes to an existing deployment, and maintainer validation. It is not an additional checklist for every new device.

Use your dedicated test hostname in place of `ha-mtls.example.net`. Keep the resource's client-certificate requirement enabled. Never use `curl -k` or disable backend verification to make a test pass.

## Optional Mac test with an issued PKCS#12 package

This helps separate device/import issues from the Pangolin/backend path. It is optional when Companion already provides the positive connection check.

A command such as `curl --cert-type P12 --cert file.p12 ...` may not prompt for the PKCS#12 password on some curl/LibreSSL builds. It can fail locally with `mac verify failure` and `HTTP 000` even though the package is valid. `000` means no HTTP response was obtained; it is not a server status code.

First verify the package and password independently:

```bash
openssl pkcs12 -in "/full/path/to/your-device.p12" -info -noout
```

Enter the password displayed when **that exact file** was issued. `-noout` checks the input without outputting credentials. If this succeeds but curl failed without asking for a password, supply it explicitly through standard input. If verification itself fails, check the file/password pairing before diagnosing Pangolin. Do not use `-nomacver` or weaken package encryption as a workaround. [OpenSSL's PKCS#12 reference](https://docs.openssl.org/3.5/man1/openssl-pkcs12/)

For the Mac's usual zsh terminal, replace the file path and hostname, then paste the following block. The password is read silently and passed to curl through a pipe rather than written into a command argument, command history or config file:

```bash
(
  printf 'Package password: '
  read -rs p12_password
  printf '\n'
  if [[ ! "$p12_password" =~ ^[A-Za-z0-9_-]+$ ]]; then
    printf 'Expected the URL-safe password generated by this app.\n'
    exit 1
  fi

  printf 'pass = "%s"\n' "$p12_password" |
    curl -q --config - \
      --cert-type P12 --cert "/full/path/to/your-device.p12" \
      --connect-timeout 10 --max-time 20 \
      --silent --show-error --output /dev/null \
      --write-out 'HTTP %{http_code}\n' \
      https://ha-mtls.example.net/
)
```

The format check matches this app's generated passwords and prevents special characters from becoming curl configuration syntax. This helper is not intended for arbitrary externally created PKCS#12 passwords. Passwords necessarily exist in local process memory; this is not a memory-erasure guarantee. See [curl's config option](https://curl.se/docs/manpage.html#--config) and [passphrase option](https://curl.se/docs/manpage.html#--pass).

Interpret the result carefully:

| Result | Meaning / next step |
| --- | --- |
| `HTTP 200` | That request obtained an HTTP response; inspect the intended HA application separately |
| Redirect or authentication status | TLS may have succeeded; check destination and normal application authentication |
| `HTTP 502` | An HTTP-speaking endpoint answered; inspect Pangolin/connector/backend TLS, SNI and routing before claiming HA access |
| Local PKCS#12/MAC error and `HTTP 000` | The identity could not be opened; no positive mTLS test took place |
| TLS client-certificate rejection | Check issuer trust, package identity, time/expiry and certificate purpose |
| DNS, timeout or server-certificate failure | Inconclusive for client authentication; resolve that layer first |

`-q` as the first curl option skips its default config file. The command uses a fresh process, sends no HA/API authentication tokens, follows no redirects, and retains normal server-certificate verification. A curl success does not establish Companion/WebSocket/background behavior.

## When deeper checks are appropriate

| Check | When to run |
| --- | --- |
| Missing client certificate | Each new protected deployment/hostname, and after meaningful trust or edge-routing changes |
| Issued identity / Companion connection | Each enrolled/replaced device; after changes affecting its route |
| Certificate signed by an unrelated CA | Maintainer/release validation; after changing trust or TLS policy |
| Forced TLS 1.2 and 1.3, invalid purpose, expiry and future validity | Compatibility/security matrix, or investigation of a relevant change |
| Non-allowlisted user, forged ingress, CSRF and direct-port denial | Automated regression/release checks; investigate after authorization/platform changes |
| App restart persistence | Initial acceptance and storage/runtime changes; repeat when investigating persistence |
| Backup restore to an isolated HA instance | Recovery/release validation and material backup/schema changes |
| CA rotation, resumed TLS and existing WebSockets | Before offering rotation or making revocation/containment claims |
| iPadOS/macOS/media/widgets/extensions | Before claiming support for those platforms/features |

An unrelated-issuer test uses a **separate disposable CA** that is never added to Pangolin's trust list. The test leaf must have a valid clientAuth chain to that disposable CA, and the probe must actually send its identity; presenting an empty certificate list would only repeat the no-certificate test. Expect a remote TLS rejection before any HTTP response. Remove disposable keys afterward. Our scoped results are in [phase-2-results.md](phase-2-results.md); use the [full experiment plan](validation-plan.md) for remaining gates.

A successful app restart does not prove backup restoration. Perform restoration on a separate isolated instance, reconcile the restored public CA identity and metadata, and verify pending exports are not resurrected. Restored automation/integrations also need isolation from production systems. Preserve the current protected backup until a recovery procedure has been validated.

No test should remove the final Pangolin CA to simulate blocking a device: that turns mTLS off. Shared-CA individual revocation is not implemented. See [enforcement limits](certificate-management.md).
